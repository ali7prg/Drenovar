# Исполняемый комплект логики и безопасная выдача наград

Статус всех модулей: **проверено отдельно; требуется интеграция в существующий сервер и клиент**. Здесь нет подключённого HTTP-обработчика, D1-миграции, сервера движения, настоящих боевых доказательств, готовых моделей или файлов анимаций. Изображения и постановочные инструкции не являются 3D-ресурсами. `reference-transaction.mjs` — работающая модель кандидатного снимка и атомарной фиксации, не готовый серверный адаптер.

## Созданные файлы

`code/forest-rescue.mjs` экспортирует константы `CAMPAIGN_ID`, `SCHEMA_VERSION`, `RESOURCES`, `TASKS`, `SITE_IDS`, `BOSS_ID`, `BOSS_SPECIES`, `HORSE_ID`, `GUARDIANS`, `TASK_REWARDS`, `PROLOGUE_REWARD`, `FINAL_REWARD`; функции `initialState`, `loadState`, `validateState`, `validateAction`, `reduceCampaign`, `siteNumber`, `siteMultiplier`, `guardianSpec`, `artifactId`, `captiveIds`, `taskReward`, `campaignMaximumReward`.

`code/reference-transaction.mjs` экспортирует `createReferenceSnapshot` и `executeReferenceCommand`. У примера свой минимальный JSON-снимок, свои receipts и отдельный wallet. **В игре использовать уже существующие players/commands/транзакцию и настоящие поля кошелька, не создавать вторую экономику.**

`tests/campaign.test.mjs` проверяет полный путь кампании, восстановление каждого шага, награды, доказательства боя, двойную трату ключа, вместимость, конкурентные claims, повторы, профили и повреждённые данные. `tests/fixtures.mjs` создаёт синтетические доверенные доказательства только для тестов. Файлы `tests/fixtures/*.json` — синтетические примеры сохранений, не реальный прогресс игроков.

Дополнительно созданы `code/mechanisms.mjs` (исполняемая логика четырёх типов поиска/механизма), `code/reserve-refill.mjs` (опциональное автоматическое пополнение после настоящей траты), а также тесты `mechanisms.test.mjs`, `reserve-refill.test.mjs`, `content-contract.test.mjs`. Последний сверяет реальные JSON кампании/экономики/локализации с кодом, включая guardian species, суммы, порядок задач, horseId и контрольные сохранения.

## Контракт сохранения

Предлагаемый **новый** namespace в доверенном серверном игроке: `p.adventures.forest_rescue_v1`. Его нет в изученном v92. Не помещать его внутрь импортируемого legacy `city`.

Поля: `schemaVersion`, `campaignId`, `phase`, `paused`, `revision`, `sites`, `rescuedIds`, `usedBattleProofs`, `escrow`. Начальная фаза `prologue`, затем `rescue`, `boss_unlocked`, `boss_active`, `completed`. `sites` содержит ровно 12 ID `lf_site_01`–`lf_site_12`. У каждого `step` от 0 до 5 и `artifact` 0/1. Соответствие шагов: 0 undiscovered, 1 discovered, 2 artifact_recovered, 3 guardian_defeated, 4 cage_opened, 5 rescued. Ключ существует при step2 и step3; открытие клетки атомарно меняет step3→4 и artifact1→0.

Постоянные ID ключей `lf_key_01`–`lf_key_12` выводятся из ID места. Клиент не выбирает, какой ключ потратить. Три спасённых каждого места имеют ID `lf_captive_01_a/b/c` и т. д. Они добавляются в `rescuedIds` только после подтверждённого прибытия домой, а не после нажатия на клетку. Это сюжетные спасённые, не бесплатные боевые единицы и не скрытое изменение населения.

Следующий акт из трёх мест открывается после `escort_home` на всех трёх местах предыдущего акта. Внутри акта места можно проходить в любом порядке. Все 12×5 задач сохраняются независимо. Босс доступен только при 36 спасённых. Для запуска финального боя нужна ратуша V; ожидаемая проверка уровня берётся с сервера. Поражение в бою не помечает задачу выполненной, не уничтожает уже полученные ключи других мест и не обнуляет кампанию. Повторный бой реализует настоящий боевой адаптер.

`loadState(undefined)` создаёт начальное состояние. `null`, неизвестная версия, отрицательные значения, дублированные доказательства и несогласованные суммы вызывают отказ без молчаливого сброса. Миграция существующего игрока — добавить отсутствующий namespace лениво. Для будущих реальных версий нужна отдельная проверенная миграция: не маскировать повреждение под «нового игрока».

`usedBattleProofs` хранит reportId и привязку к месту либо финальному боссу. Один отчёт не может закрыть два боя. `validateState` проверяет форму и инварианты, но **не доказывает подлинность входного состояния**. Оно всегда загружается из серверной базы, никогда из JSON клиента.

## Команды

Wire-формат для существующего `/api/command`:

```json
{"kind":"adventure","campaignId":"forest_rescue_v1","action":"attempt_task","siteId":"lf_site_01","taskId":"recover_artifact"}
```

Действия: `discover_horse`; `attempt_task` с `siteId` и `taskId`; `begin_boss`; `finish_boss`; `claim_rewards`; `pause`; `resume`. Внутри reducer поле действия называется `type`. `taskId` выполняется строго в порядке `discover`, `recover_artifact`, `defeat_guardian`, `unlock_cage`, `escort_home`. Артефакт добывают во время исследования до боя; открыть клетку можно только после подтверждённой победы.

Разрешены только точные поля указанной формы. Клиент не передаёт `state`, `evidence`, `battleProof`, `reward`, `wallet`, `capacity`, `ownerId`, `playerId`, `now`, `revision`, `artifact` и количества ресурсов. Команда `finish_boss` лишь просит сервер проверить условие; сама по себе победу не подтверждает.

Повтор того же ключа и того же JSON возвращает текущее авторитетное состояние и кошелёк без повторного эффекта. Изменение тела при том же ключе отклоняется. Подпись в примере, как в существующем `CoreGameServer.command`, — `JSON.stringify(body)`, включая порядок полей. Не менять правила старых receipts задним числом. Даже после удаления старых receipts новый ключ не повторит награду выполненной задачи: её step/phase служит долговременным запретом повторной выплаты.

## Доверенные условия: их необходимо подключить к настоящей игре

`reduceCampaign(state, action, trustedContext)` не использует часы. В `trustedContext` сервер передаёт:

- `authenticatedPlayerId`: выбранное поселение после проверки сессии/аккаунта, не заголовок пользователя произвольного внешнего Worker.
- `arrival`: `{ownerId,targetId,serverVerified:true,routeValid:true}`. Считать доказательство из серверного маршрута и достигнутой позиции. Target для лошади `lf_horse_origin`, для места его ID, для ключа `lf_key_XX`, для клетки `lf_site_XX:cage`, для арены `lf_boss_ancient_maw`. Не принимать клиентские координаты, время прибытия, distance или булевый `serverVerified`.
- `battleProof`: `{reportId,encounterId,ownerId,siteId,species,level,modifier,serverVerified:true,finalized:true,outcome:"victory"}` и `expectedEncounterId` из серверной привязки конкретного стража. Проверить завершение по настоящему серверному бою, владельца, species/level, уникальный отчёт и принадлежность арене. У финального босса species `ancient_maw`, siteId `lf_boss_ancient_maw`; его нельзя подменить Тенерисом с другой картинкой. Для него уровень необязателен в reference-proof, поскольку это новый отдельный профиль боя.
- `escortProof`: `{ownerId,siteId,captiveIds:[точная тройка],serverVerified:true,arrivedHome:true}`. Сервер обязан подтвердить маршрут конвоя, отсутствие телепорта/пропуска препятствий, сохранённое состояние сопровождения и прибытие всех троих. Флаг не является доказательством сам по себе.
- `mechanismProof`: `{ownerId,siteId,serverVerified:true,solved:true}`. Для `recover_artifact` требуется одновременно правильное прибытие к ключу и сохранённое решение механизма именно этого места. Одного клика на артефакт недостаточно. Верифицировать через новый server-owned mechanism namespace, описанный ниже.
- `hallLevel`: рассчитанный сервером уровень ратуши; для стражей I/II/III проверяются 1/3/5.
- `wallet`, `capacity`: только для `claim_rewards`, рассчитанные из актуального серверного города в той же транзакции.

Эти структуры — **требования к новым адаптерам**, не существующие функции движка и не криптографические attestations. Пример намеренно не выдаёт синтетические test-fixtures за реальную проверку пути/боя. В адаптере разрешено автоматически вызвать доменную команду после серверного события, но с тем же transaction/receipt договором.

## Большие ресурсные награды без потери на переполнении

Пользователь запросил очень большие награды. Размеры не уменьшать молча. Полная кампания начисляет **7 515 000** единиц: food 2 325 000; wood 2 385 000; stone 1 590 000; iron 1 025 000; coins 190 000. Сюда входят 60 задач, пролог и финал. Это щедрая новая экономика по запросу, **не подтверждённый баланс**. XP не добавляется. Политика первой настоящей победы: сохранить штатную добычу боя отдельно от бонуса задачи и явно показать её отдельной строкой боевого отчёта. Сумма 7 515 000 относится только к гарантированным бонусам кампании, не к совокупному луту всех боёв. Новые campaign guardians одноразовые: после подтверждённой победы не возрождать их для повторного фарма; существующую обычную охоту не менять. `additionalHiddenCampaignAwards:false` запрещает скрытые дополнительные бонусы кампании, а не штатную видимую добычу боя.

Награда сначала атомарно записывается в `escrow.earned` и `escrow.pending`. `escrow.claimed` содержит уже переведённое в настоящий кошелёк. Для каждого ресурса всегда выполняется `earned = claimed + pending`. Сумма earned проверяется по реально завершённым шагам. Отдельный ползунок количества не нужен: `claim_rewards` переводит по каждому ресурсу `min(pending, max(0, capacity - wallet))`.

Остаток не исчезает, не истекает и не требует повторного прохождения. Полный склад — успешный нулевой перевод с объяснением «Склад заполнен; награда сохранена». Уже существующий баланс выше cap не урезать. Кнопка получения доступна и после завершения/паузы кампании. Показывать отдельно «Начислено», «Получено» и «Осталось получить», чтобы миллионы обещанных ресурсов не выглядели немедленно доступными при малом складе.

Пример конкурентного claim: два запроса прочли 5000 food в escrow и пустой склад cap2000. Оба подготовили перевод 2000, но фиксируется только один revision CAS. Второй заново читает кошелёк2000 и pending3000, после чего переводит0 либо возвращает receipt. Нельзя применять оба кандидатных эффекта вне CAS.

### Автопополнение без тысяч повторных нажатий

Создан и проверен чистый helper `refillAfterVerifiedSpend` в `code/reserve-refill.mjs`. Настройка игрока предлагается как **новое отдельное поле** `p.rewardReservePrefs.forest_rescue_v1.autoRefill`, default `false`; она не входит в строгую схему кампании. Интерфейс должен дать осознанный переключатель «Автоматически пополнять склад из наград после расходов» и отдельную кнопку ручного `claim_rewards` / «Пополнить все ресурсы».

После штатной успешной платной команды (например, строительства или обучения) внутри **той же** серверной транзакции: снять кошелёк непосредственно до списания и после него, затем вызвать helper с `authenticatedPlayerId`, `optedIn`, `beforeWallet`, `afterWallet`, актуальной пятикомпонентной `capacity`. Возвращённые campaign state и wallet сохранить вместе с той же квитанцией исходной команды. Existing production settlement должен выполниться до снимка beforeWallet; нельзя смешивать начисление производства/возврат и списание в этих двух снимках.

Функция требует реального уменьшения хотя бы одного ресурса и отклоняет смесь увеличений/списаний. При `optedIn:false`, отсутствии расходов или полном кошельке резерв не тратится. Она переносит доступный остаток до обычной вместимости по всем пяти ресурсам. Остаток остаётся в escrow; деньги сверх вместимости сохраняются. Успешные затраты определяет существующая игровая логика — сравнение двух кошельков само по себе не доказывает разрешённую покупку.

Не вызывать helper по таймеру, каждому poll, клиентскому сигналу «я потратил» или на возврате средств. Не платить цену напрямую из escrow и не разрешать покупку, которая до пополнения не прошла штатную проверку средств/склада. Пользователь может сначала вручную заполнить склад; цены и вместимость остаются прежними. При CAS-конфликте повторить настоящую команду и расчёт пополнения на новом снимке, не применять старый перевод. Нужна отдельная owner-scoped команда сохранения настройки; она ещё не подключена к существующему API.

### Исполняемые механизмы артефактов

`code/mechanisms.mjs` экспортирует `initialMechanism(site)`, `validateMechanism(state, site)`, `reduceMechanism(state, {symbol}, site, trusted)`. `site` берётся только из доверенного `data/campaign.json`, не из запроса. Все 12 решений проверены тестами. Хранить состояние отдельно: новый namespace `p.adventureMechanisms.forest_rescue_v1`, ключи по siteId, в том же CAS. Не добавлять неизвестные поля внутрь строгого campaign state.

Механизм доступен после `discover`, **до боя** со стражем. `trusted` требует проверенную личность, `siteDiscovered:true`, `siteAccessVerified:true`; при paused новые вводы отклоняются. Для `trail_cache` каждый символ должен совпасть с настоящим `observedLandmark`, который сервер получает из проверенного пути. Для `rune_lock` и `winch_sequence` обрабатывается точная последовательность трёх действий. Для `paired_latch` перед финальным центральным затвором дополнительно обязательны **одновременно** `leftOccupied:true`, `rightOccupied:true`, `occupancyServerVerified:true`, рассчитанные по текущему серверному состоянию двух допустимых участников/объектов. Сохранённое посещение двух плит не заменяет одновременное удержание.

Ошибка сбрасывает только попытку механизма, не платит награду и не тратит артефакт. После решения сохраняется `solved`; повторный ввод не повторяет эффект. Сам helper не выдаёт ключ: его получает отдельный `attempt_task/recover_artifact` после проверенных mechanismProof и arrival. Нужен новый owner-scoped wire-handler ввода символа, который загрузит site/state из сервера и составит доверенный контекст. Физическая доступность ориентиров, серверные датчики плит и устройство лебёдки ещё требуют реализации в реальной сцене.

## Жизненный цикл, анимации и восстановление

Сценические длительности, crossfade и положение камеры не являются условиями получения ресурсов. Сервер сначала принимает задачу и сохраняет её; клиент показывает соответствующее событие. Если анимация пропущена, вкладка закрылась или сеть пропала, задача и награда остаются в подтверждённом состоянии. После reload восстановить устойчивые позы: нужный артефакт скрыт/видим, замок открыт, спасённые отсутствуют в клетке, боссы показывают актуальный статус. Не воспроизводить повторно выдачу награды по локальному таймеру.

`pause`/«Отложить» сохраняет кампанию и запрещает новые её шаги до `resume`; получение уже начисленных наград остаётся доступным. Оно **не останавливает существующие общие бои, обучение, производство и серверное время DRENOVAR**. Сам reducer не запускает нападения и не вводит потери за уход приложения в фон. Настоящие активные бои продолжают работать по правилам проекта; описать это пользователю перед отправкой войска.

Постановочные события: `horse_joined`, `task_completed`, `boss_unlocked`, `boss_started`, `campaign_completed`, `reward_escrowed`, `transfer_rewards`. Одноразовые визуальные события дедуплицировать по campaign/revision/action, а состояние объектов брать из авторитетного namespace. Анимационные файлы в этом комплекте не обещаны: Claude Code создаёт их по референсам и спецификации.
